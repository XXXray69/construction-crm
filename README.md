# СтройКонтроль — мини-CRM «Объекты и задачи»

React + TypeScript + Vite + Ant Design + Supabase (Auth, PostgreSQL, RLS).

## Быстрый старт

1. `npm install`
2. Создайте облачный проект на https://supabase.com/dashboard
3. В **SQL Editor** выполните `supabase/migrations/001_init.sql` (один раз).
4. **Authentication → Providers → Email:** выключите **Allow new users to sign up** (открытая регистрация).
5. **Authentication → Users → Add user:** вручную создайте три учётные записи с подтверждённым email: одного постановщика и двух исполнителей.
6. В **SQL Editor** добавьте профили, подставляя UUID из Authentication → Users:

```sql
insert into public.profiles (id, full_name, role) values
('UUID_ПОСТАНОВЩИКА', 'Руководитель', 'manager'),
('UUID_ИСПОЛНИТЕЛЯ_1', 'Алексей', 'worker'),
('UUID_ИСПОЛНИТЕЛЯ_2', 'Мария', 'worker');
```

7. Создайте `.env` в корне по шаблону `.env.example`. Значения берите в **Project Settings → API Keys** и **Project Settings → Data API** (Supabase URL). Используйте **publishable/anon** key, **НЕ service_role/secret**.
8. `npm run dev` — откройте адрес в терминале.
9. Войдите как постановщик и создайте 2–3 объекта и задачи, назначив разных исполнителей. Чтобы сделать разные статусы, войдите под исполнителями и проведите некоторые задачи через кнопки переходов.

## Правила

- Постановщик видит все объекты и задачи, создаёт и редактирует их, назначает исполнителей, принимает или возвращает задачи с обязательным комментарием.
- Исполнитель видит только свои задачи и объекты, на которых ему назначены задачи. Может выполнять только предписанные переходы статуса.
- `public.profiles.role` не редактируется из клиентского API; выдаётся администратором через SQL.
- RLS закрывает чтение/запись на сервере; дополнительный trigger `guard_task_write` проверяет полномочия, неизменяемые поля и разрешённые переходы.
- `change_task_status` безопасно обрабатывает изменения статусов в одной транзакции, а trigger `record_task_history` фиксирует актёра из его сессии. Клиент не имеет write-доступа к истории.
- Регистрация должна быть **выключена вручную** в панели Supabase — SQL миграция этого не делает.

## Самопроверка безопасности

1. Войти исполнителем №1 — у него нет задач и объектов исполнителя №2, если задачи не пересекаются по объектам; общий объект виден только если в нём есть собственная задача.
2. Попробовать обновить чужую задачу по ID через Supabase REST — RLS не позволит.
3. Попробовать `new → accepted` через REST — trigger отклонит, даже если ID свой.
4. Попробовать `review → revision` без комментария — сервер отклонит.
5. Попробовать `INSERT / UPDATE / DELETE` в `task_history` под authenticated — нет write-grants и RLS-policy.
6. Попробовать вручную изменить `created_by`, `assignee_id`, `description` от имени исполнителя — trigger отклонит.

## Сборка и деплой

```sh
npm run build
```

GitHub: `git init`, `git add .`, `git commit -m "Initial construction CRM"`, создайте пустой GitHub репозиторий и подключите его командами, которые покажет GitHub. **Не коммитьте `.env`.**

Vercel: Import Git Repository → Framework: Vite → Environment Variables (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`) → Deploy. Приложение использует единый маршрут `/`, поэтому дополнительных rewrite-правил не требуется.

## Решения и допущения

- Роль назначает только администратор вручную.
- Создание задачи всегда устанавливает статус `new`, смена статуса выполняется только по допустимому циклу.
- Постановщик может редактировать название/описание/объект/исполнителя задачи, но не автора и дату создания.
- Удаление объекта удаляет его задачи и историю их статусов (каскадное удаление).
- Принятая задача считается завершённой; переходов из неё нет.
- Начальное создание задачи не считается сменой статуса и не добавляется в историю переходов.
- Отдельного журнала изменений полей (кроме статуса) нет: ТЗ требует только историю статусов.
